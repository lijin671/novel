# 拆书续写工作台 v1 设计

- 日期：2026-05-07
- 状态：已确认设计，待实现计划
- 适用项目：`c:\ITS\MuMuAINovel`
- 主题：整本 TXT 上传后生成“续写圣经”，用于忠实续写为主、同设定扩写为辅的小说二创

## 1. 背景

当前仓库已经有拆书二创入口、忠实续写风格提炼、章节分析、记忆检索、角色/组织数据结构，但“整本小说 -> 结构化续写底座 -> 按底座稳定续写”这条链还没有真正闭环。

现状更像：

`TXT 导入 -> 建项目 -> 直接尝试续写`

这会导致几个老问题反复出现：

- 原书人物味道容易散
- 剧情推进手感续不上
- 世界观/组织/时间线抽得不够稳
- 伏笔和未回收因果缺少统一账本
- 分析结果存在，但没形成真正可编辑、可执行的“接盘圣经”

## 2. 目标

打造一条以“忠实续写”为主的拆书工作流：

`TXT 上传 -> 原书解析 -> 续写圣经 -> 人工确认/微调 -> 续写规划 -> 章节续写`

核心目标：

1. 自动抽出原书可续写的结构化底座
2. 默认先产出“续写圣经”，而不是直接开写
3. 让后续续写优先守住：
   - 人物不崩
   - 剧情推进手感接近原书
   - 世界观/组织/时间线不吃书
   - 伏笔和因果链可追踪
4. 在不破坏现有项目架构的前提下，复用当前 `book_remix`、章节、记忆、风格体系

## 3. 非目标

本设计第一版不追求：

- EPUB / Markdown / ZIP 等多格式导入
- 多 Agent 大编排系统
- 自动修复所有原书冲突
- 完整百科级静态角色库
- 重写整个章节生成主链

## 4. 用户确认过的产品决策

### 4.1 功能定位

- 忠实续写优先
- 同设定扩写保留，但放在第二优先级

### 4.2 原书味道优先级

第一梯队：

- 人物不崩
- 剧情推进手感

第二梯队：

- 文风口吻
- 设定一致
- 伏笔因果

### 4.3 续写圣经策略

- 上传整本后，必须先生成“续写圣经”
- 圣经确认后再进入正式续写

### 4.4 圣经内容范围

全量覆盖以下模块，其中 `1/2/3/4/5/6/8` 优先：

1. 世界观与规则
2. 人物卡
3. 组织/势力
4. 时间线
5. 主线/支线故事线
6. 伏笔与未回收因果
7. 文风与叙事手感分析
8. 续写硬约束

### 4.5 原书冲突处理

- 系统只标注冲突和疑点
- 默认不擅自修正
- 后续由用户确认采用哪一版事实

### 4.6 输入范围

- 第一版只支持 `TXT`

### 4.7 圣经使用形态

- 采用“半编辑型”
- 可编辑：
  - 人物卡
  - 时间线
  - 主线/支线
  - 伏笔
  - 续写硬约束
- 只读为主：
  - 文风分析
  - 原书统计项
  - 自动抽取解释项

### 4.8 续写启动方式

- 同时支持“直接续写”和“先续写规划再续写”
- 默认走“先规划再出章节”

## 5. 名词定义

### 5.1 续写圣经

不是普通读后感，也不是全书摘要，而是一份“为续写服务的结构化执行底座”。重点是：

- 什么不能改
- 什么还没收
- 人物下一步大概率怎么动
- 后续生成必须遵守哪些边界

### 5.2 拆书续写工作台

指围绕 `book_remix` 扩出的专用工作流，用于：

- 原书结构抽取
- 圣经生成
- 圣经审阅
- 续写规划
- 正文续写

## 6. 推荐方案

采用 **方案 B：拆书续写工作台**。

不选方案 A（小修小补）的原因：

- 只能继续堆补丁
- 圣经很容易变成旁路分析结果，无法真正约束后续续写

不选方案 C（多 Agent 工厂）的原因：

- 第一版复杂度过高
- 容易做成不稳定花架子

方案 B 的特点：

- 保持现有项目主架构不变
- 给拆书续写单独建立稳定中间层
- 先把“原书 -> 圣经 -> 规划 -> 续写”的骨架搭牢

## 7. 总体架构

新增一条明确的工作流：

1. 原书解析层
2. 续写圣经生成层
3. 圣经审阅工作台
4. 续写规划层
5. 章节生成层

### 数据流概览

`TXT 上传`
-> `章节切分与原书解析`
-> `圣经结构化抽取`
-> `用户审阅/编辑`
-> `生成续写规划`
-> `按规划生成正文`

## 8. 模块设计

### 8.1 原书解析层

职责：

- 解析 TXT
- 切分章节
- 识别卷/阶段边界
- 抽取标题、人物候选、组织候选、时间表达、剧情节点

输入：

- `TXT`

输出：

- 规范章节列表
- 原书解析摘要
- 候选人物/组织/事件节点

边界：

- 只做原材料整理
- 不在这里决定续写方向

### 8.2 续写圣经生成层

职责：

- 将原书解析结果压缩为“可执行续写底座”

输出结构：

1. 世界观与规则
2. 人物卡
3. 组织/势力
4. 时间线
5. 主线/支线故事线
6. 伏笔与未回收因果
7. 文风/叙事手感摘要
8. 续写硬约束
9. 冲突与疑点清单

关键要求：

- 面向“后续怎么写”组织内容
- 不是机械摘要
- 不得把冲突点自动写死为单一事实

### 8.3 圣经审阅工作台

职责：

- 让用户在正式续写前掌控最关键的事实层

第一版可编辑模块：

- 人物卡
- 时间线
- 主线/支线
- 伏笔
- 续写硬约束

第一版只读模块：

- 文风分析
- 自动统计与解释说明

设计原因：

- 保留人工接管能力
- 避免第一版 UI 过胖
- 允许用户纠正 AI 抽错的人物、线索、顺序

### 8.4 续写规划层

职责：

- 先输出“下一阶段怎么写”，再进入章节生成

建议输出：

- 续写总方向
- 下一阶段目标
- 下一卷/下一段规划
- 关键冲突
- 需优先回收的伏笔
- 不可越界的设定边界

默认策略：

- 用户确认圣经后，默认先出规划
- 同时允许提供“快速直续”入口

### 8.5 章节生成层

职责：

- 基于圣经与规划生成正文

生成输入优先级建议：

1. 用户当前明确要求
2. 续写硬约束
3. 当前续写规划
4. 人物卡与关系
5. 伏笔与未回收因果
6. 最近章节上下文
7. 忠实续写风格锚点
8. 文风分析摘要

关键要求：

- 不允许只靠“最近几章 + 通用 prompt”裸写
- 必须正式纳入圣经约束

## 9. 续写圣经结构草案

### 9.1 世界观与规则

- 时代/背景
- 核心规则
- 世界边界
- 不可打破的设定
- 关键场景与常见活动空间

### 9.2 人物卡

每个核心人物至少包含：

- 核心标签
- 动机/利益
- 说话方式
- 行动模式
- 关键关系
- 当前状态
- 易崩点
- 续写注意事项

### 9.3 组织/势力

- 成立背景
- 目标与利益
- 层级结构
- 与其他组织关系
- 当前作用

### 9.4 时间线

- 重要事件顺序
- 相对/绝对时间
- 关键转折节点
- 当前停靠点

### 9.5 主线/支线

- 主线目标
- 当前阶段冲突
- 支线与主线绑定关系
- 不可随意删除的支线

### 9.6 伏笔与未回收因果

- 伏笔内容
- 起始章节
- 当前状态
- 推荐回收窗口
- 若不回收的断层风险

### 9.7 文风与叙事手感摘要

- 叙事视角
- 常用句式倾向
- 对话密度
- 爽点释放方式
- 情绪推进方式
- 章节收尾习惯

### 9.8 续写硬约束

- 不能改的设定
- 不能 OOC 的人物
- 必须延续的冲突
- 优先回收的伏笔
- 必须保持的叙事边界

### 9.9 冲突与疑点清单

- 人物前后不一致
- 时间线冲突
- 组织设定变动
- 伏笔疑似弃坑
- 其他疑点

默认处理：

- 标注
- 不擅改
- 等待用户确认

## 10. 数据模型建议

第一版不强行重构现有章节/角色/组织主表，建议新增“拆书续写中间层”。

建议新增逻辑实体：

- `BookRemixBible`：圣经主记录
- `BookRemixBibleCharacter`
- `BookRemixBibleOrganization`
- `BookRemixBibleTimelineEvent`
- `BookRemixBibleStoryArc`
- `BookRemixBibleForeshadow`
- `BookRemixBibleConstraint`
- `BookRemixBibleConflict`
- `BookRemixContinuationPlan`

设计原则：

- 原书解析结果与项目正式角色/组织表解耦
- 圣经可反复刷新，但人工修订字段要能保留
- 后续章节生成读取圣经，不要求强行把所有圣经内容先灌回普通业务表

## 11. 与当前仓库的兼容边界

### 11.1 可复用

- `book_remix` 上传与建项目入口
- `txt_parser_service`
- 当前章节、项目、角色、组织、记忆、写作风格体系
- 忠实续写风格回落能力
- `chapter_context_service`
- `novel_workflow_service` 后续可接续写审查

### 11.2 需要新增

- 圣经数据模型
- 原书解析结果到圣经的生成器
- 圣经审阅 UI
- 续写规划器
- 章节生成对圣经的正式接线

### 11.3 第一版不建议动

- 全量重写章节 API 主链
- 一上来并入所有外部资料格式
- 复杂多 Agent 编排

## 12. 错误处理与回退

### 12.1 原书自身冲突

- 写入“冲突与疑点清单”
- 不自动修

### 12.2 TXT 切章不准

- 允许人工重切/合并/拆分章节

### 12.3 人物/组织抽取不全

- 允许候选提升为核心项
- 允许人工补录

### 12.4 文风提炼不稳

- 文风只作为锚点，不得压过人物/剧情/设定约束

### 12.5 原书过长

- 不直接整本塞模型
- 采用“分层抽取 -> 圣经汇总 -> 续写时按需取用”

## 13. 测试与验收建议

### 13.1 第一版验收样例

选择 2-3 本已经断更、且用户熟悉原书味道的 TXT 作为测试集。

### 13.2 核心验收点

1. 能否稳定切章并建出拆书项目
2. 能否生成完整圣经骨架
3. 人物卡是否比当前拆书结果更稳
4. 是否能列出关键主线/支线/伏笔
5. 是否能显式标出原书冲突点
6. 圣经编辑后，续写规划是否反映修改
7. 续写首批章节是否明显优于“无圣经直续”

### 13.3 回归重点

- 不破坏现有 `book_remix` 基础导入能力
- 不破坏现有章节生成与分析链
- 不破坏项目默认风格回落逻辑

## 14. 实施顺序建议

推荐顺序：

1. 原书解析结果补强
2. 圣经数据模型与存储
3. 圣经生成器
4. 圣经审阅 UI
5. 续写规划器
6. 章节生成接入圣经
7. 验收与调优

## 15. 明确不做的错误方向

- 不把“续写圣经”做成只有总结没有约束的报告
- 不继续靠单次超级 prompt 硬续
- 不把冲突点悄悄自动修掉
- 不在第一版就做成百科式巨型后台
- 不为了看起来智能而引入不必要的多 Agent 复杂度

## 16. TaskIntentDraft

- 目标：完善更偏向拆书二创、忠实续写的能力
- 输入：整本太监小说 TXT
- 输出：可审阅、可部分编辑、可正式约束续写的“续写圣经”
- 风险：当前项目已有功能多、工作区脏、容易把分析结果做成旁路而非主约束
